# Vision: окремий Coding Agent

**Статус:** APPROVED власником 25.09.2026 для scope і Design DoD · **Редакція:** 1.0 · **Робоча назва:** Standalone Coding Agent (SCA). Назва не є брендовим рішенням. Документ визначає цілі й межі окремого проєкту, а не змінює Vision, ADR чи backlog NODREN. Схвалення дизайну не означає вибір рушія чи дозвіл змінювати NODREN.

## 1. Призначення

SCA — локальний інструмент для допомоги у написанні коду **NODREN та інших Git-репозиторіїв**. Власник задає конкретну задачу, сам вибирає API та модель, контролює дозволені дії й витрати. Інструмент знаходить потрібний код, готує обмежені правки, перевіряє їх і показує diff, тести та використання токенів для людського прийняття рішення.

Це **не** внутрішній `Software` Agent NODREN, не 14-й агент його системи й не обов’язкова залежність NODREN Core. Спроможність SCA редагувати код не розширює повноважень у цільовому репозиторії.

## 2. Власник, користування, очікуваний результат

Перший користувач — власник проєкту; один інтерактивний запуск працює з одним репозиторієм та одним завданням. Початковий інтерфейс — CLI з читабельним ходом роботи, поточною моделлю, використанням токенів, видимими причинами зупинки та фінальним reviewable diff. Інші розробники й публікація на GitHub — можливий наступний крок, якщо ліцензії, документація й безпека це дозволяють.

**Вимірюваний результат:** завершені за критеріями прийняття задачі; збережені сторонні зміни; простежуваність кожного модельного виклику й дозволеної файлової/термінальної дії; вартість і токени на *прийняту* задачу, порівняні з контрольним запуском тієї самої моделі. Економію у відсотках наперед не обіцяємо.

## 3. Scope і вимоги до MVP

| ID | Рішення про scope | Як це спостерігати |
|---|---|---|
| CA-R01 | Окремий локальний проєкт для довільного Git repo; NODREN — перший цільовий repo з додатковими правилами. | Успішний запуск на тестовому repo і окремий preflight NODREN без обходу його правил. |
| CA-R02 | Явний task contract: мета, authoritative sources, scope, must-do, must-not, acceptance, дозволені перевірки, stop rule. Шлях `tasks/task-XXX.md` — запропонований формат, **не наявний стандарт NODREN**. | Неповна/суперечлива задача зупиняється до редагування. |
| CA-R03 | Власник вручну задає точні provider/API endpoint/model для запуску. Повторний запуск може використовувати інший вибір; автоматичний router і прихований fallback заборонені. | Відтворюваний run record; trace не містить виклику незаданої моделі. Плавна зміна посеред запуску — V2. |
| CA-R04 | Відкриті GitHub-проєкти використовуються як dependency, зовнішній CLI або перевірений патерн; engine **не вибрано**. | Кожен вибраний компонент має rationale, pinned version, ліцензію і тест інтеграції. |
| CA-R05 | Контроль контексту: пошук, вибіркове завантаження, ліміти на великі результати tools, збереження обов’язкових вимог; прозоре використання prompt cache, коли доступний. | Звіт показує джерела контексту; негативні вимоги не зникають; usage і cache hits заміряні. |
| CA-R06 | Usage per task/model call з provenance: provider reported, engine reported або estimate; input/output/cache/reasoning лише якщо є відповідні поля. Відсутній прайс = `UNKNOWN`. | Немає обліку `UNKNOWN` як $0 і немає подвійного підрахунку кешу; видимий task total. |
| CA-R07 | Налаштовувані ліміти кроків, вихідних токенів у межах підтримки engine, часу й soft budget із зупинкою **перед наступним контрольованим кроком**. | Відповідний негативний сценарій зупиняється; UI пояснює, чому це не абсолютна гарантія витрат. |
| CA-R08 | Безпечна робоча копія, перевірений edit/patch, збереження dirty files, перевірка і фінальний diff/evidence. | Тести на конфлікт, path escape, невдалий patch і збій перевірки; людський review до зовнішніх дій. |
| CA-R09 | Repo policy вищий за task file; NODREN має власні канонічні джерела, issue, branch та phase gates. | Негативний NODREN-кейс із `p1_authorized=false` не запускає P1 runtime edit. |

**Рішення про жорсткий грошовий ліміт [відкрите]:** strict pre-call USD cap можливий лише коли обраний backend дає контроль над **кожним** API-викликом, включно з внутрішніми summary/retry. Це окремий критерій експерименту й V2-кандидат, а не обіцяна властивість будь-якого CLI. Для MVP монітор показує фактично доступну гранулярність; якщо неможливо довести облік кожного виклику, не можна заявляти «live per-call monitoring».

## 4. Поза межами початкового проєкту

- Інтеграція в NODREN Core/Tool Gateway/13 агентів; реалізація внутрішнього NODREN `Software` Agent.
- Самостійний вибір дешевшої моделі, непомітний fallback, автоматичні витрати на інші моделі.
- Загальний багатокористувацький API gateway, billing-платформа, автоматичний деплой, merge, push і надсилання повідомлень.
- Векторна база для кожного repo, масова команда паралельних агентів, власний tokenizer для всіх provider, форк великого engine без доказу необхідності.
- Заява про повний sandbox тільки тому, що існує Git worktree. Недовірений shell потребує окремої ізоляції.

## 5. Принципи дизайну

1. **Людина задає мету, модель і межі.** Система записує фактичний вибір для кожного запуску.
2. **Repo rules діють у repo.** Локальні інструкції можуть посилювати task spec; зовнішній агент не змінює їхню ієрархію.
3. **Видимі докази.** Результатом є diff, фактичні exit codes та usage з позначенням джерела, а не лише повідомлення моделі «готово».
4. **Ставка на готові відкриті рішення.** Копіювання коду з GitHub — окреме рішення з ліцензійним і maintenance аналізом; власний код заповнює лише виявлені прогалини.
5. **Міра ефективності — прийнята задача.** Порівнювати USD/токени/час разом із коректністю та регресіями.

### Працюючого MVP — Product DoD (майбутній)

- [ ] На тестовому Git-репозиторії агент виконує task spec, робить вузький diff, запускає справжні дозволені перевірки й дає traceable report; **два перевірені API-провайдери** і щонайменше одна модель кожного доступні для ручного вибору в окремих запусках через обраний engine або адаптери. Вибір має бути реальним, без прихованих викликів третьої моделі.
- [ ] Записує всі **контрольовані та спостережувані** model calls і суму за задачу; перевірена повнота трасування саме вибраного engine. Невідомі usage/ціна не подаються як нуль, soft budget/step stop демонструється негативним тестом.
- [ ] Task rules і заборони цільового repo працюють: dirty files збережено, неавторизовані branch/shell/external дії блокуються, NODREN gate не обходиться.
- [ ] Patch conflict, crash/timeout, API failure і повторне відкриття run дають явний безпечний стан та зрозумілий звіт; немає прихованого commit/push.
- [ ] Виконано зафіксований benchmark якості та витрат і перевірку залежностей/ліцензій. Не заявлено економію, яку не підтверджено вимірюванням.

**Зовнішні дослідницькі джерела:** окремі документи `NODREN_Coding_Agent_Design_and_Roadmap_UA_2026-09-25.md` та `NODREN_Coding_Agent_Research_Pack_2026-09-24.md` зберігаються поза цим пакетом. **Відкриті питання:** назва, ОС першого MVP, два providers для інтеграційного тесту, конкретний engine, потреба у strict cap і допустимі команди для першого repo. Вони не блокують описаний scope, але рішення фіксують після дослідницького етапу.
