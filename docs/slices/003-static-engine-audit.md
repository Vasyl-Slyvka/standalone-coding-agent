**Статус: документаційний слайс, 25.09.2026.** Це підготовка до S02b, **не порівняльний запуск**: жоден рушій не встановлено, API не викликано, вартість/якість/економію токенів не виміряно. Авторизований scope — [`task-S02B-STATIC.md`](../../tasks/task-S02B-STATIC.md). Критерії SCA беруться з [Vision](../../VISION.md), [Roadmap](../../ROADMAP.md), [Implementation Map](../../IMPLEMENTATION_MAP.md), [AGENTS.md](../../AGENTS.md); живі задачі NODREN підпорядковуються його власним інструкціям.

## Факти SCA й метод перевірки

Власник вручну задає API/provider, endpoint і модель на запуск; приховані fallback, summary/title/commit calls до іншої моделі неприйнятні (CA-R03). Потрібні контроль дозволених дій, збереження dirty files, review diff і реальні перевірки (CA-R05, CA-R08). Запис usage має розрізняти provider/engine reported та estimate, а невідомий прайс — `UNKNOWN` (CA-R06); зупинка перед *наступним контрольованим кроком* є soft budget, а не гарантією граничного рахунка (CA-R07). MVP вимагає двох перевірених API-провайдерів, але які саме — ще відкрите питання. Чинний [стенд S02a](../../benchmarks/README.md) задає фікстури й схему результату, без реального model call.

Нижче **джерело** означає офіційні документи або код на точному Git revision; **висновок** є інженерним припущенням про SCA; **gate** — те, що потребує живої негативної перевірки. HEAD зафіксовано 25.09.2026; гілки рухаються, тому pinned SHA використовувати при відтворенні, релізну версію й транзитивні залежності фіксувати окремо. Жоден із документованих лічильників сам по собі не доводить повноту *всіх* API-викликів.

## Три архітектури залишаються кандидатами

| Шлях | Перевага як гіпотеза | Місце контролю і конкретне питання для spike |
|---|---|---|
| A. Тонкий wrapper над CLI | Менше власного коду, готовий цикл edit/test. | Wrapper запускає фіксовану команду, збирає JSON/log/diff; чи можна заборонити всі небажані дії та виклики, не втручаючись у engine? Чи достатня гранулярність usage? |
| B. CLI + supervisor SCA | Task parser, context/permissions, журнал, verification і stop logic поза engine. | Supervisor обмежує workspace/процес, корелює telemetry; якщо CLI породжує внутрішні calls, supervisor без проксі/SDK не бачить їх. Перевірити, чи реально відрізати shell/network. |
| C. Малий API loop + готові libraries | SCA може охопити кожен API query й tool dispatch власним дозволом. | Вища реалізаційна/maintenance вартість: retry, контекст, редагування, sandbox, provider adapters. mini-SWE-agent лише прототип механіки; перевірити підтримку двох API та якість/вартість на однаковій задачі. |

Жоден рядок не є рекомендацією обрати рушій. Конкретні можливості залежать від конфігурації й версії; негативний результат одного candidate не доводить перевагу іншої архітектури.

## Телеметрія, ефективність токенів та дозволи: контракт spike

1. Записати вручну обрані provider, model, endpoint alias, engine SHA/release, OS, config snapshot **без секретів**, дозволені файли й бюджет. На кожен task окремий одноразовий repo з [S02a fixtures](../../benchmarks/README.md); `base_head` і dirty file hash до/після. Два API провайдери — окремі прогони. Коли однакова модель/API недоступна всім підходам, `unpaired`, а не порівняння USD як рівних.
2. Реєструвати зовнішнім watcher/провайдерським usage export кількість запитів, модель, токени, cache, retries і час, якщо такий канал доступний; зіставляти за run ID/time з engine events. Поки немає незалежного повного джерела, `trace_completeness=uncorrelated` навіть якщо engine повідомляє `usage`. У разі прихованого summary/commit/retry call або розбіжності залишити incident і перевірити конфігурацію. Без такого каналу не заявляти повноту чи жорсткий cap.
3. Нормалізувати provider-reported, engine-reported і estimate окремо. `cached_input` може бути частиною input, reasoning може входити до output; не додавати їх вдруге. Відсутність поля/прайсу лишається `UNKNOWN`. Для підпискового CLI еквівалент за API-тарифом — *estimate*, не рахунок підписки. Звіт за кроком і завданням показує ліміт, причину зупинки й останній доступний usage; engine з post-step stop не може обіцяти точний USD ceiling.
4. Для перевірки економії зробити парні контрольні прогони: весь необхідний контекст vs `rg`/selective file loading, однакові модель/task/permission/checks; у Aider опцію `--map-tokens 0` можна використати як baseline без repo map. Порівнювати **токени й орієнтовну вартість на прийняте завдання**, latency, failed attempts і регресії. Prompt cache оцінювати лише за provider-reported cache hits; summary persistence, repo map і pruning залишити гіпотезами до виміру.
5. Матриця негативних кейсів: заборонені write/read/command/network; symlink та path escape; prompt injection у README; збереження dirty/untracked; API timeout/429/invalid key; відсутній прайс/usage; fallback або background model; failed tests; cancel під час виклику; спроба commit/push. `deny/ask` у тексті конфігурації не гарантує ОС-ізоляції. Git worktree відокремлює Git-зміни, але не shell, секрети й мережу. Мінімальна підстава прийняття — фактично заблоковані дії, review diff і журнал команд/exit code.

## Рішення після реального S02b, а не зараз

| Критерій | Pass для переходу R1 → R2 | Якщо не доведено |
|---|---|---|
| Модель/API | Ручна фіксація і два реально перевірені API, без сторонніх model calls. | Залишити прототипом або замінити шов. |
| Контроль дій | Shell/write/network поза дозволеним scope фактично заблоковано; dirty збережено. | Відкласти інтеграцію з живими repo. |
| Usage/budget | Зрозуміла provenance й обмеження повноти trace, `UNKNOWN`, soft-stop перевірено. | Не стверджувати per-call coverage чи економію. |
| Якість та витрати | Парні прийняті задачі, реальні тести і diff review, tokens/cost/latency/невдачі. | Архітектуру не вибирати за деклараціями. |
| Ліцензії | Release та транзитивні залежності збережено з notices. | Не включати код/пакет у публічний реліз. |

**Невідомі операційні входи:** ОС першого MVP, два обрані вручну provider/API та моделі, допустимий бюджет, чи є незалежний usage export, мінімальний набір shell-команд і вимога strict cap. **Наступний слайс:** реальний S02b лише після фіксації цих входів; без них можна й далі готувати офлайнові фікстури/перевірки, але не оголошувати gate виконаним.
