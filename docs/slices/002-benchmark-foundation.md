# S02a — офлайновий benchmark foundation

**Статус:** реалізовано локальний стенд. **S02b/R1 відкриті:** жодного реального рушія або API-провайдера не порівнювали, вартість і виграш токенів не вимірювали. Вимоги і task scope — [`tasks/task-S02A.md`](../../tasks/task-S02A.md).

## Результат

- Чотири одноразові синтетичні Git-репозиторії: арифметична правка, залежна правка у двох файлах, dirty файл та prompt injection у README. У вихідному стані тести навмисно не проходять; це приймальна задача для майбутнього рушія, не дефект фікстури.
- Офлайновий reader JSON-запису кандидата перевіряє provider/model/endpoint alias на кожному видимому call; не додає cache/reasoning до input/output, повертає `UNKNOWN` для відсутнього usage/прайсу і вимагає provenance для визначеної вартості. Суперечливі status/exit code та необґрунтований claim повноти trace відхиляються.
- [`benchmarks/README.md`](../../benchmarks/README.md) задає парні умови, негативні кейси, quality gate, provenance та відкриті питання; лише фактичні запуск і незалежний audit можуть підтримати вибір engine.

## Перевірка

Виконати `PYTHONPATH=src:. python3 -m unittest discover -s tests -v`, `git diff --check`, `PYTHONPATH=src:. python3 -m sca.benchmark benchmarks/example-record.json`. Для фікстури `two-files` упевнитися, що обидва тести падають з `AssertionError`, а не помилкою імпорту. Приклад запису має `calls=[]` і повертає `UNKNOWN`; це **не** виміряний результат.

## Межі й наступний gate

S02a не дає дозволу запускати команди у NODREN, не ізолює довільний shell і не доводить, що CLI розкриває всі внутрішні виклики. Для S02b потрібні зафіксовані OS/версії кандидатів, manual provider/model, граничні витрати й окреме спостереження за викликами. До цього часу три архітектурні підходи залишаються відкритими.
