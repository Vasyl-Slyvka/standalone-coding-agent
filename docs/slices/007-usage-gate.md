# S03b — офлайновий облік і м’яка зупинка

**Стан:** реалізовано незалежне від рушія рішення для наступного контрольованого кроку. Живий S02b/R1 лишається відкладеним; це **не** виконаний повний S03 або Product DoD. Scope: [`task-S03B-USAGE-GATE.md`](../../tasks/task-S03B-USAGE-GATE.md).

## Вхід і запуск

`sca.usage_gate` читає локальний JSON до 64 KiB із `schema_version: 1`, `selection` (`provider`, `model`, `endpoint_alias`), `limits` (`max_steps`, `max_elapsed_ms`, `soft_cost_usd` як десятковий рядок USD або `null`), `elapsed_ms` та масивом `steps`. Кожен видимий step має унікальний `step_id`, ту саму трійку вибору, `input_tokens`/`output_tokens` (ціле число або `null`), `cost_usd` (десятковий рядок або `null`), `cost_provenance` і `price_source`. Відомий cost потребує джерела й одного з `provider_reported`, `engine_reported`, `estimate`; невідомий має `unknown` і `null` source. Ніяких ключів, prompt чи повних відповідей у record не зберігати.

```bash
PYTHONPATH=src python3 -m sca.usage_gate /path/to/usage-record.json
```

Якщо після записаних кроків досягнуто max steps, max elapsed або soft USD cost, повертається `SOFT_STOP` з причинами; при невідомій вартості під заданою грошовою межею також зупиняється **наступний** крок. Без cost cap невідома вартість лишається `UNKNOWN`, але сама по собі не блокує наступний крок. Відсутність записаних кроків не означає нульових витрат: навіть із cap `$0` результат дозволяє *перший* крок, бо це лише post-step policy. Вартість підсумовується через `Decimal`; проміжні джерела не перетворюються на рахунок провайдера чи залишок підписки. Відсутні токени не стають нулем.

## Що саме доведено

Синтетичні тести перевіряють рішення за кроками, часом, ціною, невідомими полями, дублем `step_id`, підміною provider/model/endpoint і помилковим price source. Вивід завжди має `trace_completeness: unverified` і пояснення `post-step soft stop; no pre-call guarantee`. Модуль не викликає API і не здатен бачити приховані повторні, фонові або допоміжні запити рушія. Під час майбутнього S02b потрібно звірити фактичні виклики з незалежним журналом, а також прив'язати рішення до справжньої контрольної точки виконання. Лише тоді можна перевіряти реальне зупинення; цей слайс демонструє **логіку рішення**, не його інтеграцію.
